# VibeLingo Plugin 产品形态设计

> 日期：2026-07-11  
> 状态：Proposed，供产品评审  
> 阶段：从研究进入产品设计；本文不定义具体 API、清单文件或工程实现  
> 初始场景：中国母语用户在 Synergy 中使用英语进行 vibe coding、vibe research 和 vibe writing

## 1. 一句话定义

**VibeLingo 是嵌入 Synergy 对话的目标语言工作支架：用户用目标语言完成真实任务，卡住时获得恰到好处的表达、理解与改写帮助，并可把真正有价值的语言时刻留到以后。**

VibeLingo 首先帮助用户继续工作，其次才帮助用户积累语言能力。它不是课程、翻译器、语法检查器或自动生成的生词本。

## 2. 要解决的问题

用户并非没有学习动机。他们希望在日常 Agent 会话中直接使用目标语言，但会在以下瞬间退回母语、交给翻译器或放弃表达：

1. **表达检索失败**：知道意思，不知道目标语言怎么说。
2. **任务精度不确定**：能写出来，但担心 Agent 理解错范围、约束或意图。
3. **局部理解失败**：理解回复的大意，却不懂决定下一步的术语、句子或逻辑关系。
4. **语域不确定**：意思基本正确，但不确定是否适合当前读者、场景和语气。
5. **改完但没学会**：看到更好的版本，却不知道改动为什么更好、下次如何自己完成。
6. **认知过载**：调试、阅读或写作压力升高时，没有余力兼顾语言质量。

产品机会不是消灭所有语言错误，而是让这些阻塞不再迫使用户离开目标语言工作流。

## 3. 产品承诺

### 3.1 核心承诺

- 用户可以先尝试，而不必等到语言足够好才开始使用目标语言工作。
- 帮助发生在当前对话和当前任务中，不要求进入独立学习模式。
- 每次响应只解决当前最重要的语言障碍。
- 修改尽量保留用户原意、原有表达和自主选择。
- 用户明确决定哪些内容值得保存、复习或长期追踪。

### 3.2 非承诺

VibeLingo 不承诺：

- 提供完整语言课程或覆盖所有能力等级；
- 自动纠正每个错误；
- 把每次 Agent 会话转化成一堂课；
- 仅凭被动使用就保证词汇增长或水平提升；
- 在没有用户确认的情况下判断用户“不会什么”；
- 替代专业翻译、学术编辑或语言教师。

## 4. 设计原则

### 原则一：工作优先

当学习收益与主任务冲突时，主任务优先。高压力状态下，VibeLingo 应减少解释、接受混合语言、快速给出可用表达。

### 原则二：用户先尝试

默认顺序是“用户表达 → 遇到障碍 → 请求帮助”。插件不在每条消息后主动点评，也不把正确但不够母语化的表达视为必须修复的问题。

### 原则三：最小有效支架

响应从最少帮助开始：提示优先于整段代写，局部解释优先于全文翻译，一条高价值原因优先于完整语法讲座。用户可以继续追问以展开更多层次。

### 原则四：语境决定正确性

“自然”不是唯一标准。coding 首先追求任务精度，research 首先追求论证准确，writing 首先追求读者和语域适配。

### 原则五：记住有价值的，不是记住一切

默认不把对话自动转化为用户画像或生词库。收藏由用户确认，保存的是可复用的表达或理解，而不是原始会话记录。

### 原则六：解释必须可迁移

解释应帮助用户下次自行完成，例如指出“`can` 后用动词原形”，而不只是宣告某个版本更自然。

## 5. 产品形态

VibeLingo 在用户眼中是一组嵌入对话的语言动作，而不是一个独立应用。

### 5.1 四个核心动作

| 用户语言 | 产品动作 | 解决的卡点 | MVP |
|---|---|---|---|
| “这个意思怎么说？” | **Help / 帮我表达** | 表达检索失败 | 是 |
| “这样写准确、自然吗？” | **Polish / 帮我改进** | 精度、语法、语域不确定 | 是 |
| “这里是什么意思？” | **Explain / 帮我理解** | 局部理解失败 | 是 |
| “这个以后提醒我。” | **Save / 保存这个语言时刻** | 有价值内容容易丢失 | 是，用户确认 |

用户不必记住正式命令。以下自然语言都应该映射到相应动作：

- “How do I say ‘这里需要兜底’ in English?”
- “帮我把这句写得更准确，但不要改变范围。”
- “这里的 `idempotent` 在当前上下文是什么意思？”
- “记住 `add a fallback` 这个表达。”

显式 `@vibe-lingo` 或快捷命令可以作为可靠入口，但不应成为唯一入口。

### 5.2 渐进式响应层级

所有动作共享同一响应结构：

1. **立即可用的答案**：先让用户继续任务。
2. **一个关键原因**：只解释当前最可迁移的点。
3. **可选展开**：替代表达、语气差异、逐词解释或练习。
4. **可选保存**：用户认为有价值时收藏。

默认响应应在数秒内可扫读完。VibeLingo 不自动附带测验、长篇规则或进度信息。

## 6. 核心交互设计

### 6.1 Help：帮我表达

#### 适用时刻

- 用户用母语或混合语言表达了意图；
- 用户卡在一个术语、短语、约束或完整句子；
- 用户希望继续用目标语言与主 Agent 沟通。

#### 默认输出

```text
推荐：We should add a fallback here.

如果强调异常处理：We should handle the failure case here.

区别：fallback 是主方案失败时采用的备用路径；failure case 更强调需要处理的失败情况。
```

#### 规则

- 默认给一个推荐表达；只有存在实质性的语义或语域差异时才给第二个。
- coding 场景必须优先保证技术含义和任务边界准确。
- 不翻译代码、标识符、路径和不应变化的专有名词。
- 如果原意有歧义，先指出两种解释，不擅自替用户选择。
- 不默认生成完整 Agent 指令；优先补齐用户卡住的部分。

### 6.2 Polish：帮我改进

#### 适用时刻

- 用户已经完成一次目标语言尝试；
- 用户担心语法、精度、自然度、语气或读者效果；
- 用户希望保留自己的意思，而不是重新生成内容。

#### 默认输出

```text
建议：Please change this function without affecting the behavior of the other modules.

关键变化：`without affecting` 比 `don't influence` 更适合描述“修改不得产生副作用”；同时明确了需要保持不变的是其他模块的行为。

你的原句已经能理解，这个修改主要提高任务边界的精度。
```

#### 规则

- 区分“错误”“可能误解”“语域选择”和“仅仅存在另一种说法”。
- 默认只突出一到两个最重要的变化。
- 不把用户声音全部改写成统一、过度正式的 Agent 文风。
- 如果原句已经足够完成任务，应明确告诉用户，不为显示价值而制造修改。
- writing 场景允许用户指定读者、语气和改写强度。

### 6.3 Explain：帮我理解

#### 适用时刻

- 用户选择 Agent 回复中的术语、短语、句子或论证关系；
- 用户需要理解其在当前任务中的具体含义；
- 用户不希望整段翻译。

#### 默认输出

```text
`stale closure`：闭包仍然引用创建时的旧值，而不是当前最新值。

在这里，它意味着回调读取了旧的 `state`，所以即使界面已经更新，回调仍按之前的数据执行。

可近似理解为：a closure that captured an outdated value。
```

#### 规则

- 先用简单目标语言或母语解释，再连接当前语境。
- 对 research 文本，必要时拆出“作者主张、证据、限定条件”。
- 对技术术语，翻译不能替代机制解释。
- 如果用户请求全文翻译，可以满足，但应把它视为用户选择的低支架模式，而非默认体验。

### 6.4 Save：保存语言时刻

收藏对象不是裸单词，而是一个最小的、可复用的**语言时刻（Learning Moment）**：

| 字段 | 含义 |
|---|---|
| 表达 | 用户希望以后会用或会认的词、短语、句型 |
| 意义 | 在本次语境中的简明含义 |
| 用法 | 一条可迁移说明或区别 |
| 示例 | 去敏后的最小语境示例 |
| 来源动作 | help、polish、explain 或用户手动添加 |
| 目标语言 | 所属语言 |

默认只在用户明确说“保存、记住、加入词库”时创建。插件可以在一次高价值帮助后显示低干扰的“可保存”提示，但不得自动写入。

原始消息、完整 Agent 回复、项目代码和文件内容不属于语言时刻，不应随收藏持久化。

## 7. 三类工作流中的形态

### 7.1 Vibe coding

#### 用户的主目标

让 Agent 正确理解并执行代码任务。

#### 高价值语言时刻

- 表达技术动作：extract、refactor、defer、fallback、work around；
- 描述范围和约束：without changing、only within、preserve existing behavior；
- 理解诊断术语：race condition、stale closure、dependency cycle；
- 在高压调试中用混合语言保持沟通。

#### 产品偏好

- 精确度高于自然度；
- 简短答案高于教学完整性；
- 允许中文描述意图、英文保留技术术语；
- 调试阶段不主动提出学习动作。

### 7.2 Vibe research

#### 用户的主目标

找到、理解、比较并综合可信信息。

#### 高价值语言时刻

- 把朴素问题转换成学术检索术语；
- 区分相邻概念和术语边界；
- 拆解复杂句中的主张、证据与限定；
- 用目标语言准确总结贡献、局限和适用范围。

#### 产品偏好

- 概念和论证准确高于表面流利；
- Explain 可比 coding 场景多一层结构化解释；
- Polish 必须避免把谨慎表述改成过强结论；
- 保存短语、术语区别和总结框架，优先于保存孤立单词。

### 7.3 Vibe writing

#### 用户的主目标

为特定读者产出准确、合适且保持个人意图的文本。

#### 高价值语言时刻

- 启动第一句或段落过渡；
- 调整正式度、直接程度和礼貌程度；
- 消除可能误解的表达；
- 发现反复依赖的安全词和句型；
- 理解改写背后的可迁移规则。

#### 产品偏好

- 用户可指定读者、语气和改写强度；
- 保留作者声音，不默认整段重写；
- 先评价原文是否已经有效，再给修改；
- 对长文本按用户选定的范围处理，不自动全篇纠错。

## 8. 状态与干预强度

插件不需要精确推断用户的心理状态，但应允许用户通过请求方式表达当前所需强度：

| 状态 | 用户信号 | 默认行为 |
|---|---|---|
| 紧急完成任务 | “直接给我一句能用的”“先解决问题” | 给答案，不展开教学 |
| 正常工作 | 普通 help / explain 请求 | 答案＋一个关键原因 |
| 主动学习 | “为什么”“还有什么区别”“让我先改” | 提示、自我修正、更多对比 |
| 深度写作 | 指定读者、语气、风格 | 提供读者效果和语域分析 |

用户不需要设置永久的“教学模式”。每次请求都可以体现当前意图，系统设置只保存语言、默认解释语言和默认响应长度等稳定偏好。

## 9. 首次使用体验

首次使用只要求最少信息：

1. 目标语言；
2. 默认解释语言；
3. 是否显示“可保存”提示。

不要求用户完成正式水平测试。初始帮助深度可以使用“简洁 / 标准 / 详细”这样的可理解选项，而不是强迫用户准确选择 CEFR 等级。

首次引导应通过一个真实例子展示：

```text
你可以直接对 Agent 说：
“How do I say ‘不要改变现有行为’ in English?”

VibeLingo 会在当前对话中帮助你继续表达。
它默认不会自动纠正消息，也不会保存完整对话。
```

## 10. MVP 边界

### 10.1 MVP 包含

- Help、Polish、Explain 三个用户发起的动作；
- 自然语言触发和一个明确、可靠的显式入口；
- 上下文感知的技术、研究和写作解释；
- 渐进式响应：答案、一个原因、可选展开；
- 用户确认的 Save；
- 最小偏好：目标语言、解释语言、响应深度；
- 用户可查看和删除自己保存的语言时刻；
- 清楚说明哪些上下文会被临时处理、哪些内容会被保存。

### 10.2 MVP 不包含

- 默认自动分析所有会话并捕获生词；
- 自动错误画像或能力等级推断；
- FSRS、Agenda 定时复习和主动通知；
- streak、积分、排行榜和每日目标；
- 全局语法检查或每条消息后的自动点评；
- 复杂进度统计；
- 多语言同时学习；
- 单独的仪表盘、课程页或学习模式；
- 自动修改用户发给 Agent 的原消息。

### 10.3 为什么这样裁剪

该 MVP 只验证一个核心命题：**语言支架能否让用户在真实工作中更长时间、更有信心地使用目标语言。**

自动捕获、复习算法和进度系统分别包含新的价值假设、隐私风险和交互成本。它们应在用户确实产生了值得保存的内容之后再验证。

## 11. 隐私与用户控制

### 11.1 默认保证

- 请求帮助时只处理完成当前动作所必需的上下文；
- 不持久化原始用户消息、完整 Agent 回复、代码块或项目文件内容；
- 只有用户确认保存的语言时刻进入持久存储；
- 保存前提供将被保存内容的可见预览；
- 用户可以编辑、删除和导出保存内容；
- 关闭或卸载插件不会隐藏仍然存在的数据位置。

### 11.2 后续自动捕获实验的进入条件

未来只有同时满足以下条件，才考虑自动捕获：

1. 用户主动开启；
2. 明确解释将分析哪些会话内容；
3. 支持项目级、会话级和临时暂停；
4. 默认只产生待确认候选，不直接进入复习；
5. 可以查看系统为什么判断某项值得保存；
6. 有足够真实收藏数据证明自动化可以减少负担而不是制造噪声。

## 12. 成功标准与失败信号

由于目前没有真实会话数据，以下是待验证指标，不是已有基线。

### 12.1 核心成功信号

- 用户在得到帮助后继续用目标语言推进同一任务；
- 响应无需多次澄清即可保留用户原意；
- 用户会重复主动使用至少一个核心动作；
- 用户认为帮助减少了切回母语或外部翻译器的需要；
- 被保存的内容在之后的真实会话中再次被使用或识别。

### 12.2 诊断指标

- 各动作的使用频率和重复使用率；
- Help 后用户采用、修改或放弃建议的比例；
- Polish 中“原句已足够有效”的比例；
- Explain 后用户是否继续原任务，而不是继续要求全文翻译；
- Save 提示被接受、忽略和关闭的比例；
- 用户请求“更短”“不要解释”或“直接替我写”的频率。

### 12.3 失败信号

- 用户觉得每次帮助都像上课；
- 用户逐渐完全依赖整段生成，不再尝试目标语言；
- Polish 经常改变任务含义或作者语气；
- Explain 只提供字面翻译，不能解决当前理解问题；
- 用户不信任插件读取上下文；
- 保存内容数量很多，但用户从未再次使用；
- 核心动作需要用户记住复杂命令才能触发。

## 13. 无真实会话时的验证方案

直接开始设计并不等于直接假定设计正确。在没有历史会话的情况下，采用“设计探针”生成第一批证据。

### 阶段 A：场景演练

为 coding、research、writing 各编写 10 个高压和低压任务场景。每个场景验证：

- 用户卡点是否真实且单一；
- 应该触发哪个动作；
- 最小响应能否让任务继续；
- 解释是否可迁移；
- 是否值得保存。

### 阶段 B：内部 dogfooding

在真实 Synergy 工作中主动使用目标语言，手动记录：

- 何时切回母语；
- 何时请求表达、改写或解释；
- 哪种响应太长、太短或改变了原意；
- 哪些内容第二天仍希望记得。

### 阶段 C：可用性原型

先验证交互，不验证完整学习系统。核心任务是确认：

- 自然语言能否稳定触发正确动作；
- 三层响应是否容易扫描；
- 用户是否理解 Save 保存的具体内容；
- coding、research、writing 是否需要不同默认输出。

### 阶段 D：决定是否进入自动化

只有在积累一定数量的真实帮助和收藏行为后，再决定：

- 自动候选提取是否必要；
- 收藏对象应以词、短语、句型还是错误模式为主；
- 是否存在真实复习需求；
- 简单重现是否足够，还是需要 FSRS。

## 14. 产品决策与待验证假设

### 当前产品决策

- VibeLingo 的首要定位是目标语言工作支架。
- 核心体验发生在 Synergy 当前对话中。
- MVP 采用用户发起的 Help、Polish、Explain。
- 收藏对象是语言时刻，而不是裸单词。
- MVP 的持久化由用户明确确认。
- 自动捕获和间隔复习不作为首个 MVP 的必要组成。

### 待验证假设

- 三类工作流可以共享一组核心动作，仅通过上下文调整输出。
- 用户愿意先尝试目标语言，再请求局部帮助。
- 一个关键原因比完整语法解释更适合工作流。
- 用户保存短语和表达的意愿高于保存孤立单词。
- 减少切回母语是一个可感知且有持续价值的结果。
- Help 可能是最早产生价值的动作，但 Polish 或 Explain 可能拥有更高的重复使用率。

## 15. 推荐的下一步

1. 评审并接受、修改或拒绝本文的六项产品决策。
2. 基于本文为 coding、research、writing 分别撰写 10 个场景脚本。
3. 设计 Help、Polish、Explain、Save 的对话级低保真原型。
4. 用内部 dogfooding 产生第一批真实会话证据。
5. 在获得证据后，再形成 MVP 规格和 Synergy 集成设计。
